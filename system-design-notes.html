01 — Foundations

Start small: the single-server setup

Every complex system starts simple. The course builds up from a single server handling one user, then scales it piece by piece — because understanding each component in isolation makes the full picture easier to reason about later.

How a request reaches your server

User types a domain

The browser or mobile app only knows a human-readable domain, e.g. app.demo.com — not an IP address.

DNS resolves the domain

The Domain Name System maps app.demo.com → the server's IP address, and returns it to the client.

Client sends an HTTP request

With the IP in hand, the client sends an HTTP request to the server asking for specific data.

Server responds

The server processes the request and replies with HTML (for browsers) or JSON (for mobile apps / APIs) — JSON is preferred for mobile because it's lightweight.

01 — Foundations

Choosing a database: SQL vs NoSQL

As the user base grows, the web tier (handling traffic) is split from the data tier (managing storage) so each can scale independently. That immediately raises the question: which kind of database?

🗄️ Relational (SQL / RDBMS)

Data lives in tables of rows and columns, like a spreadsheet. Examples: PostgreSQL, MySQL, Oracle, SQLite.

📦 Non-relational (NoSQL)

Optimized for flexible, fast access to large volumes of unstructured data. Examples: MongoDB, Cassandra, Redis, Neo4j.

Why SQL: joins & ACID transactions

SQL databases support join operations — combining rows from multiple tables (e.g. joining customers and products into an orders table). They also guarantee strong consistency through ACID transactions:

LetterPropertyMeaning
AAtomicThe whole transaction succeeds completely, or fails completely — never partially.
CConsistentEvery transaction moves the database from one valid state to another valid state.
IIsolatedConcurrent transactions don't interfere with each other.
DDurableOnce committed, data survives even a server crash.

The four NoSQL families

📄 Document stores

MongoDB — JSON-like documents holding complex nested data in a single record.

📊 Wide-column stores

Cassandra, Cosmos DB — tables with dynamic columns; excellent for massive scale and heavy write throughput.

🔗 Graph stores

Neo4j (Amazon uses Neptune) — stores entities and relationships as graphs; great for recommendations.

⚡ Key-value stores

Redis, Memcached — simplest and fastest; typically in-memory, ideal for caching and sessions.

Decision guide

If your application needs…Choose
Well-structured data with clear relationships (e.g. e-commerce customers & orders)SQL
Strong consistency & transactional integrity (e.g. banking, finance)SQL
Super low-latency responsesNoSQL
Unstructured / semi-structured data (JSON blobs), loose relationshipsNoSQL
Flexible, massively scalable storage (e.g. recommendation / activity data)NoSQL
01 — Foundations

Vertical vs horizontal scaling

⬆️ Vertical scaling ("scale up")

Add more RAM/CPU to the same server. Simple, works for low/moderate traffic — but hits a hard resource ceiling, and gives you zero redundancy: if that one server dies, the whole app dies with it.

➡️ Horizontal scaling ("scale out")

Add more servers to share the load. Better fault tolerance (one server can fail while others keep serving) and scales further — but now you need something to route traffic across them.

Load balancing

A load balancer sits in front of your server pool and distributes incoming traffic so no single server is overwhelmed — while also rerouting traffic away from any server that's down.

Seven load-balancing strategies

01

Round Robin

Requests rotate sequentially: server 1 → 2 → 3 → back to 1. Simple; best when all servers have equal specs.

02

Least Connections

Sends the next request to whichever server currently has the fewest active connections. Good for variable-length sessions.

03

Least Response Time

Combines responsiveness and active connection count to pick the fastest available server.

04

IP Hash

Hashes the client's IP to consistently route the same client to the same server — useful for server-side session data.

05

Weighted (Round Robin / Least Conn.)

Servers get weights based on capacity (RAM, CPU); higher-weighted servers receive proportionally more traffic.

06

Geographic

Routes each request to the server closest to the user's location — reduces latency for global services.

07

Consistent Hashing

Maps clients onto a "hash ring" of servers, so a given client consistently lands near the same server — resilient when servers are added/removed.

Health checks

Load balancers continuously ping each backend server. If a server stops responding, it's marked offline and excluded from routing until it passes a health check again.

Real-world examples

TypeExamplesNote
SoftwareNGINX, HAProxyInstalled & configured on your own server; NGINX doubles as a web server.
HardwareF5, CitrixDedicated physical appliances known for high performance.
Cloud-managedAWS ELB, Azure LB, Google Cloud LBComes with automatic scaling, security, and built-in health monitoring.
01 — Foundations

Single point of failure (SPOF)

A SPOF is any one component whose failure takes the entire system down with it — a single shared database, or a single load balancer, are classic examples.

📉 Reliability

One failure can cause full outages and direct business losses.

📈 Scalability

Every added component adds another risk of becoming the next SPOF.

🔓 Security

Attackers can target the single choke point directly to bring the whole system down.

Removing the load balancer as a SPOF

1 · Redundancy

Run more than one load balancer; if one fails, traffic shifts to the other.

2 · Health checks

Monitor load balancers themselves, not just backend servers.

3 · Self-healing

Automatically replace a failed load balancer with a fresh instance — no manual intervention.

Database SPOFs

Handled separately with replication/failover strategies (covered in the course's dedicated databases module).

What is an API, and which style should you use?

02 — API Design

Four design principles for a great API

The guiding rule: the best API is one developers can use without reading the documentation.

1 · Consistency

Consistent naming, casing, and patterns across every endpoint — don't mix camelCase and snake_case.

2 · Simplicity

Focus on core use cases; minimize complexity so the design is intuitive at a glance.

3 · Security

Authentication, authorization, input validation, and rate limiting are non-negotiable baseline features.

4 · Performance

Design for efficiency: caching, pagination, minimal payloads, and fewer round trips.

Your protocol choice shapes what's possible: HTTP unlocks REST's verbs and status codes; WebSocket unlocks real-time, bidirectional APIs; gRPC (over HTTP/2) accelerates service-to-service calls.

Application-layer protocols

Application protocols sit above TCP/UDP and define message formats, request/response patterns, and connection handling.

HTTP & HTTPS

HTTPS = HTTP + TLS/SSL encryption. It protects data in transit, adds integrity and authentication, and carries SEO benefits — it's the standard for any production server.

The consumer pulls messages whenever it has capacity — decoupling producer speed from consumer speed. Exchange types include direct (one-to-one), fan-out, and topic-based.

03 — Protocols

Transport layer: TCP vs UDP

Below the application layer sits the transport layer — the protocols that actually move packets across the network.

TCP three-way handshake

SYN

Client sends a connection request to the server.

SYN-ACK

Server acknowledges and syncs back.

ACK

Client acknowledges — the connection is now established and data can flow.

TCPUDP
DeliveryGuaranteed — lost packets are resent, order preservedNot guaranteed — lost packets are simply skipped
ConnectionConnection-based (handshake required)Connectionless
SpeedSlower (more overhead)Faster, lightweight
Best forBanking, payments, auth, general APIsVideo calls, live streaming, online games
Rule of thumb: if losing a packet would corrupt correctness (money, auth, user data) → TCP. If losing a packet just means a tiny visual/audio glitch you can skip past → UDP.
04 — Deep Dive

Designing RESTful APIs

Resource modeling

Model your business domain as nouns, not verbs: products, orders, reviews — never /getProducts.

RequestMeaning
GET /api/productsCollection of products
GET /api/products/123A single product
GET /api/products/123/reviewsNested resource — reviews for that product

Filtering, sorting & pagination

GET /products?category=electronics&inStock=true      // filtering
GET /products?sort=price_asc                          // sorting
GET /products?page=2&limit=10                         // pagination (page/limit)
GET /products?offset=20&limit=10                       // pagination (offset/limit)
GET /products?cursor=eyJpZCI6MTAwfQ                    // cursor-based pagination

This keeps responses small, saves bandwidth, and pushes sorting logic to the backend where it belongs — the frontend shouldn't have to fetch 1,000 records just to sort them.

CRUD via HTTP methods

GETReadYesGET /products
POSTCreateNoPOST /products

PATCHPartial updateYes*PATCH /products/123

Status codes

RangeMeaningCommon codes
2xxSuccess200 OK · 201 Created · 204 No Content
3xxRedirection301 Moved Permanently

5xxServer error500 Internal Server Error

Best practices checklist

  • Use plural nouns for resources (/products, not /product)
  • Use the correct HTTP method instead of encoding the action in the URL (no /deleteUser)
  • Support filtering, sorting, and pagination on collection endpoints
  • Version your API explicitly (/api/v1/...) so breaking changes don't break existing clients
04 — Deep Dive

Designing GraphQL APIs

GraphQL was built at Facebook to solve REST's over/under-fetching problem: instead of many endpoints, there's one endpoint, and the client describes exactly the shape of data it wants.

Schema & type system

type User {
  id: ID!
  name: String!
  posts: [Post!]!
}

type Query {
  user(id: ID!): User          // like GET
}

type Mutation {
  createUser(name: String!): User   // like POST/PUT/PATCH/DELETE
}

A query in action

query {
  user(id: "123") {
    name
    posts { title }
    followers { name }
  }
}

One request, exactly the fields needed — no extra images, no unused metadata, no separate calls for posts and followers.

Error handling is different

GraphQL always returns 200 OK, even on error. Failures show up inside an errors array instead, alongside any partial data that did succeed:

{
  "data": { "user": null },
  "errors": [
    { "statusCode": 404, "message": "Not found", "path": ["user"] }
  ]
}

Best practices

  • Keep schemas small and modular
  • Limit query nesting depth to avoid runaway, expensive queries
  • Use clear, meaningful names for types and fields
  • Use dedicated input types for mutations

REST vs GraphQL at a glance

RESTGraphQL

VersioningExplicit (/v1, /v2)Usually schema evolves without versioning

Common confusion, cleared up: JWT is a token format, not an authentication method by itself. "Bearer" just means "whoever holds this token gets access" — it's a pattern, and JWT is the most common bearer token. OAuth 2.0 is an authorization framework, not authentication.

Access tokens + refresh tokens

Why two tokens?

Access token

Short-lived (15 min – 1 hr). Sent with every API call.

Refresh token

Long-lived (days/weeks). Stored in an HttpOnly cookie — never localStorage, to avoid XSS theft — and used only to mint a new access token when the old one expires.

OAuth 2.0 vs OpenID Connect (OIDC)

Delegated access vs. federated login
OAuth 2.0
→
"Can this app read my Google Drive files?" → returns an access token (authorization only)
OpenID Connect
→
"Sign in with Google" → returns access token + an ID token (JWT) that proves identity

The ID token is what makes OIDC an authentication layer on top of OAuth 2.0 — the access token alone only proves permission, never who the user is.

Single Sign-On (SSO)

SSO is a UX pattern, not an authentication method: log in once with an identity provider (e.g. Google), then access Gmail, Drive, Calendar, YouTube without logging in again. Underneath, SSO relies on identity protocols:

SAML

XML-based; common in enterprise/legacy systems (Salesforce, corporate dashboards).

OpenID Connect

Modern approach, returns a JWT ID token — what most consumer "Sign in with…" flows use today.

05 — Identity & Security

Authorization — controlling what you can do

Once identity is confirmed, authorization decides which resources and actions that identity is allowed to touch.

RBAC — Role-Based

Users are assigned roles (admin, editor, viewer), each with a fixed permission set. The most common model — used by GitHub repo access, CMS tools, dashboards.

ABAC — Attribute-Based

Access is decided from attributes: user department, resource classification, time of day, device, location. More flexible than RBAC, but more complex to manage.

ACL — Access Control List

Each individual resource carries its own permission list (e.g. "Alice: read-only, Bob: read+write"). Highly specific — this is how Google Drive sharing works — but harder to scale to millions of resources.

How it's enforced: OAuth 2.0 & tokens

Delegated authorization example — connecting GitHub to Vercel

Request access

You ask GitHub to let a third-party app (Vercel) access specific repos.

Consent & scope

You choose exactly what it can do — read-only, or read + push, but not delete.

Token issued, not password

GitHub issues an access token encoding those permissions — your credentials are never shared.

Tokens (JWT/bearer) are just the mechanism that carries identity and claims (roles, scopes, expiry). The authorization model — RBAC, ABAC, or ACL — is the policy layer that decides what those claims are allowed to do.

05 — Identity & Security

Seven techniques to protect your APIs

"APIs are like doors into your system" — left unprotected, anyone can walk in.

01

Rate limiting

Cap requests per endpoint, per user/IP, and overall — prevents brute force and mitigates DDoS floods, including from distributed bot networks.

02

CORS

Controls which domains a browser is allowed to call your API from — blocks malicious sites from riding your users' sessions.

03

SQL / NoSQL injection defense

Never concatenate raw user input into a query. Use parameterized queries or an ORM's built-in safeguards.

04

Firewalls (e.g. AWS WAF)

Sits between incoming traffic and your API, blocking known attack signatures — suspicious SQL keywords, malformed methods, etc.

05

VPNs for private APIs

Internal-only APIs (like an admin dashboard) are only reachable from within the company network.

06

CSRF protection

A CSRF token, checked alongside the session cookie, stops malicious sites from submitting hidden requests using a logged-in user's cookie.

07

XSS prevention

Sanitize and escape any user-submitted content (like comments) before it's rendered back to other users, so injected scripts can't execute.
