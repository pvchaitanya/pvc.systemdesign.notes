A structured guide covering system foundations, database selection, scaling, load balancing, API design, network protocols, authentication, authorization, and API security.

01 — Foundations

Start small: the single-server setup

Every complex system starts simple. A single server can handle requests for a small application, but as traffic grows, individual components must be separated and scaled.

How a request reaches your server

The browser or mobile app uses a human-readable domain such as app.demo.com.

DNS resolves the domain

DNS maps the domain name to the server's IP address.

The client sends a request to the server.

Server responds

The server processes the request and returns HTML or JSON.

01 — Foundations

Choosing a database: SQL vs NoSQL

As an application grows, the web tier and data tier can be separated so they can scale independently.

🗄️ Relational (SQL)

Data is stored in tables containing rows and columns. Examples include PostgreSQL, MySQL, Oracle, and SQLite.

📦 Non-relational (NoSQL)

Designed for flexible schemas and large-scale workloads. Examples include MongoDB, Cassandra, Redis, and Neo4j.

Why SQL: joins & ACID transactions

SQL databases support joins and transactional guarantees through the ACID model.

Letter Property Meaning
A Atomic The transaction succeeds completely or fails completely.
C Consistent Data moves from one valid state to another.
I Isolated Concurrent transactions do not interfere incorrectly.
D Durable Committed data survives failures.

Four NoSQL families

01

Document stores

MongoDB stores JSON-like documents.

02

Wide-column stores

Cassandra and similar systems are designed for large-scale workloads.

03

Graph stores

Neo4j stores entities and relationships as graphs.

04

Key-value stores

Redis and Memcached provide extremely fast key-value access.

Decision guide

If your application needs... Choose
Structured data with clear relationships SQL
Strong consistency and transactions SQL
Flexible or semi-structured data NoSQL
Large-scale distributed workloads NoSQL

Add more RAM or CPU to the same server. It is simple, but eventually reaches hardware limits.

Load-balancing strategies

01

Round Robin

Requests rotate sequentially between servers.

02

Least Connections

Sends traffic to the server with the fewest active connections.

03

Least Response Time

Selects a responsive server based on performance.

04

IP Hash

Uses the client's IP to consistently select a server.

05

Weighted

More powerful servers receive a larger share of traffic.

06

Geographic

Routes users toward geographically closer servers.

07

Consistent Hashing

Helps maintain stable routing when servers are added or removed.

Health checks

Load balancers periodically check backend servers. An unhealthy server can be removed from routing until it recovers.

01 — Foundations

Single point of failure

A single point of failure is a component whose failure can bring down the entire system.

📉 Reliability

A single failure can cause a complete outage.

📈 Scalability

Critical components should avoid becoming bottlenecks.

🔓 Security

Central choke points can become attractive attack targets.

02 — API Design

What is an API?

An API is a contract between a client and a server. It defines how requests are made and what responses should look like.

Style Model Best for
REST Resource-based API using HTTP methods. Web and mobile applications.
GraphQL Client specifies the desired response shape. Complex data-driven applications.
gRPC RPC framework using HTTP/2 and protocol buffers. Internal service-to-service communication.
02 — API Design

Four API design principles

1 · Consistency

Use consistent naming, casing, and patterns.

2 · Simplicity

Keep APIs easy to understand and use.

3 · Security

Include authentication, authorization, validation, and rate limiting.

4 · Performance

Use pagination, caching, and efficient payloads.

03 — Protocols

TCP vs UDP

TCP and UDP operate at the transport layer.

TCP three-way handshake

SYN

Client requests a connection.

SYN-ACK

Server acknowledges the request.

ACK

Client acknowledges and the connection is established.

TCP UDP
Delivery Reliable and ordered Not guaranteed
Connection Connection-oriented Connectionless
Speed More overhead Lower overhead
Examples Web, APIs, payments Streaming, games, calls
Rule of thumb: Use TCP when reliability matters. Use UDP when low latency matters more than guaranteed delivery.
04 — Deep Dive

Designing RESTful APIs

Resource modeling

Model resources as nouns rather than actions.

Request Meaning
GET /api/products Get products.
GET /api/products/123 Get one product.
GET /api/products/123/reviews Get reviews for a product.

Filtering, sorting & pagination 

GET /products?category=electronics
GET /products?sort=price_asc
GET /products?page=2&limit=10
GET /products?offset=20&limit=10
GET /products?cursor=abc123

CRUD via HTTP methods

Method Purpose Example
GET Read GET /products
POST Create POST /products
PUT Replace PUT /products/123
PATCH Partial update PATCH /products/123
DELETE Remove DELETE /products/123

Status codes

Range Meaning Examples
2xx Success 200, 201, 204
3xx Redirection 301
4xx Client error 400, 401, 404
5xx Server error 500

Best practices

  • Use plural nouns for resources.
  • Use the correct HTTP method.
  • Support filtering, sorting, and pagination.
  • Version APIs when breaking changes are required.
04 — Deep Dive

Designing GraphQL APIs

GraphQL allows clients to request exactly the fields they need through a strongly typed schema.

Schema 

type User {
  id: ID!
  name: String!
  posts: [Post!]!
}

type Query {
  user(id: ID!): User
}

Example query 

query {
  user(id: "123") {
    name
    posts {
      title
    }
  }
}

Best practices

  • Keep schemas modular.
  • Limit query nesting depth.
  • Use clear type and field names.
  • Use dedicated input types for mutations.

REST vs GraphQL

REST GraphQL
Endpoints Multiple Usually one
Response shape Server-defined Client-defined
Related data May require multiple requests Can be requested together
Versioning Often explicit Schema evolution
05 — Identity & Security

Authentication

Authentication answers: Who is making this request?

Method How it works
Basic Auth Sends username and password credentials.
API Keys A unique key identifies the client.
Sessions Server maintains session state.
JWT Signed tokens carry claims and expiration information.
OAuth 2.0 / OIDC Standards for delegated authorization and identity.
Important: JWT is a token format, while OAuth 2.0 is an authorization framework. OpenID Connect adds an authentication layer on top of OAuth 2.0.

Access and refresh tokens

Access token

Usually short-lived and sent with API requests.

Refresh token

Longer-lived token used to obtain a new access token.

Single Sign-On

SSO allows users to authenticate once through an identity provider and access multiple applications.

05 — Identity & Security

Authorization

Authorization determines which resources and actions an authenticated user is allowed to access.

RBAC

Role-Based Access Control assigns permissions through roles such as admin, editor, or viewer.

ABAC

Attribute-Based Access Control uses user, resource, device, location, or other attributes.

ACL

Access Control Lists define permissions for individual resources.

Authorization flow

Authenticate

Verify the identity of the requester.

Read permissions

Determine the roles or scopes associated with the user.

Check authorization

Determine whether the requested action is allowed.

Allow or deny

Grant access or return an appropriate error.

05 — Identity & Security

Protecting APIs

APIs should be protected using multiple layers of security.

01

Rate limiting

Limits how many requests a client can make.

02

CORS

Controls which browser origins can access an API.

03

Injection protection

Use parameterized queries and safe database APIs.

04

Web Application Firewall

Filters suspicious or malicious HTTP traffic.

05

Private APIs

Restrict internal APIs through private networks or VPNs.

06

CSRF protection

Protect state-changing requests that use browser cookies.

07

XSS prevention

Escape and sanitize untrusted content before rendering it.

Security principle: Never rely on a single security mechanism. Authentication, authorization, validation, rate limiting, secure transport, and monitoring should work together.
