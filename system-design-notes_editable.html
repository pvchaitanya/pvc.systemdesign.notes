01 — Foundations

Start small: the single-server setup

Every complex system starts simple. The course builds up from a single server handling one user, then scales it piece by piece — because understanding each component in isolation makes the full picture easier to reason about later.

How a request reaches your server

User types a domain

The browser or mobile app only knows a human-readable domain, e.g. app.demo.com — not an IP address.

DNS resolves the domain

The Domain Name System maps app.demo.com to the server's IP address and returns it to the client.

Client sends an HTTP request

With the IP in hand, the client sends an HTTP request to the server asking for specific data.

Server responds

The server processes the request and replies with HTML for browsers or JSON for APIs.

01 — Foundations

Choosing a database: SQL vs NoSQL

As the user base grows, the web tier handling traffic is split from the data tier managing storage so each can scale independently. That immediately raises the question: which kind of database?

🗄️ Relational (SQL / RDBMS)

Data lives in tables of rows and columns, like a spreadsheet. Examples: PostgreSQL, MySQL, Oracle, SQLite.

📦 Non-relational (NoSQL)

Optimized for flexible, fast access to large volumes of unstructured data. Examples: MongoDB, Cassandra, Redis, Neo4j.

Why SQL: joins & ACID transactions

SQL databases support join operations — combining rows from multiple tables. They also guarantee strong consistency through ACID transactions.

Letter Property Meaning
A Atomic The whole transaction succeeds completely, or fails completely.
C Consistent Every transaction moves the database from one valid state to another.
I Isolated Concurrent transactions don't interfere with each other.
D Durable Once committed, data survives a server crash.

The four NoSQL families

📄 Document stores

MongoDB — JSON-like documents holding complex nested data in a single record.

📊 Wide-column stores

Cassandra, Cosmos DB — excellent for massive scale and heavy write throughput.

🔗 Graph stores

Neo4j — stores entities and relationships as graphs; great for recommendations.

⚡ Key-value stores

Redis, Memcached — simple and fast, ideal for caching and sessions.

Decision guide

If your application needs… Choose
Well-structured data with clear relationships SQL
Strong consistency & transactional integrity SQL
Super low-latency responses NoSQL
Unstructured / semi-structured data NoSQL
Flexible, massively scalable storage NoSQL

Vertical vs horizontal scaling

⬆️ Vertical scaling — "scale up"

Add more RAM/CPU to the same server. Simple and useful for low/moderate traffic, but eventually reaches a hard resource ceiling and provides zero redundancy.

➡️ Horizontal scaling — "scale out"

Add more servers to share the load. This improves fault tolerance and allows much greater scaling.

Load balancing

A load balancer sits in front of your server pool and distributes incoming traffic so no single server is overwhelmed, while rerouting traffic away from servers that are down.

Seven load-balancing strategies

01

Round Robin

Requests rotate sequentially between servers.

02

Least Connections

Sends the request to the server with the fewest active connections.

03

Least Response Time

Picks the fastest available server.

04

IP Hash

Consistently routes the same client to the same server based on IP hashing.

05

Weighted

More powerful servers receive proportionally more traffic.

06

Geographic

Routes users to servers closest to their location.

07

Consistent Hashing

Maps clients onto a hash ring and minimizes redistribution when servers change.

Health checks

Load balancers continuously ping backend servers. If a server stops responding, it is marked offline until it passes a health check again.

Real-world examples

Type Examples Note
Software NGINX, HAProxy Installed and configured on your own server.
Hardware F5, Citrix Dedicated physical appliances.
Cloud-managed AWS ELB, Azure LB, Google Cloud LB Automatic scaling and health monitoring.
01 — Foundations

Single point of failure (SPOF)

A SPOF is any one component whose failure takes the entire system down with it. A single shared database or single load balancer are classic examples.

📉 Reliability

One failure can cause full outages.

📈 Scalability

Added components can become new SPOFs.

🔓 Security

Attackers can target single choke points.

Removing the load balancer as a SPOF

1 · Redundancy

Run more than one load balancer.

2 · Health checks

Monitor load balancers themselves.

3 · Self-healing

Automatically replace failed instances.

Database SPOFs

Use replication and failover strategies.

02 — API Design

What is an API, and which style should you use?

An API is a contract between client and server: what requests can be made and what responses to expect. It hides implementation details behind a clean boundary.

Style Model Best for Trade-off
REST Resource-based and stateless. Web and mobile applications. Related data may require multiple requests.
GraphQL Single endpoint with client-defined responses. Complex UIs. Harder caching and query complexity.
gRPC RPC over HTTP/2 and protocol buffers. Internal microservices. Limited browser support.

02 — API Design

Four design principles for a great API

The guiding rule: the best API is one developers can use without reading the documentation.

1 · Consistency

Consistent naming, casing, and patterns.

2 · Simplicity

Focus on core use cases and minimize complexity.

3 · Security

Authentication, authorization, validation, and rate limiting are baseline requirements.

4 · Performance

Use caching, pagination, minimal payloads, and fewer round trips.

Protocol choice shapes what is possible: HTTP supports REST verbs and status codes; WebSocket enables real-time bidirectional APIs; gRPC is useful for service-to-service communication.

03 — Protocols

Transport layer: TCP vs UDP

Below the application layer sits the transport layer — the protocols that move packets across the network.

TCP three-way handshake

SYN

Client sends a connection request.

SYN-ACK

Server acknowledges and responds.

ACK

Client acknowledges and the connection is established.

TCP UDP
Delivery Guaranteed and ordered. Not guaranteed.
Connection Connection-based. Connectionless.
Speed More overhead. Faster and lightweight.
Best for Banking, payments, authentication, APIs. Video calls, streaming, games.
Rule of thumb: if losing a packet would corrupt correctness, use TCP. If losing a packet only causes a minor visual/audio glitch, UDP may be appropriate.
04 — Deep Dive

Designing RESTful APIs

Resource modeling

Model your business domain as nouns, not verbs: products, orders, reviews.

Request Meaning
GET /api/products Collection of products.
GET /api/products/123 Single product.
GET /api/products/123/reviews Reviews for that product.

Filtering, sorting & pagination 

GET /products?category=electronics&inStock=true
GET /products?sort=price_asc
GET /products?page=2&limit=10
GET /products?offset=20&limit=10
GET /products?cursor=eyJpZCI6MTAwfQ

Pagination keeps responses small, saves bandwidth, and prevents the frontend from fetching unnecessary data.

CRUD via HTTP methods

Method Purpose Idempotent? Example
GET Read Yes GET /products
POST Create No POST /products
PUT Full update Yes PUT /products/123
PATCH Partial update Yes* PATCH /products/123
DELETE Remove Yes DELETE /products/123

Status codes

Range Meaning Common codes
2xx Success 200 OK · 201 Created · 204 No Content
3xx Redirection 301 Moved Permanently
4xx Client error 400 · 401 · 404
5xx Server error 500 Internal Server Error

Best practices checklist

  • Use plural nouns for resources.
  • Use the correct HTTP method.
  • Support filtering, sorting, and pagination.
  • Version your API explicitly.
04 — Deep Dive

Designing GraphQL APIs

GraphQL solves REST's over-fetching and under-fetching problem by allowing clients to describe exactly the data they need.

Schema & type system 

type User {
  id: ID!
  name: String!
  posts: [Post!]!
}

type Query {
  user(id: ID!): User
}

type Mutation {
  createUser(name: String!): User
}

A query in action 

query {
  user(id: "123") {
    name
    posts { title }
    followers { name }
  }
}

One request can return exactly the fields required.

Error handling

GraphQL commonly returns a response containing both data and an errors array when something fails. 

{
  "data": {
    "user": null
  },
  "errors": [
    {
      "statusCode": 404,
      "message": "Not found"
    }
  ]
}

Best practices

  • Keep schemas small and modular.
  • Limit query nesting depth.
  • Use meaningful names.
  • Use dedicated input types.

REST vs GraphQL

REST GraphQL
Endpoints Many One
Response shape Fixed Client-defined
Related data Often multiple requests One request
Versioning Often explicit Schema evolution
Caching HTTP caching Application-level caching

05 — Identity & Security

Authorization — controlling what you can do

Once identity is confirmed, authorization decides which resources and actions that identity can access.

RBAC — Role-Based

Users are assigned roles such as admin, editor, or viewer.

ABAC — Attribute-Based

Access is based on user, resource, device, location, time, or other attributes.

ACL — Access Control List

Each resource maintains its own permission list.

Delegated authorization

Request access

A third-party application requests permission.

Consent & scope

The user chooses what the application can do.

Token issued

The provider issues a token representing the granted permissions.

Tokens carry identity and claims. The authorization model — RBAC, ABAC, or ACL — determines what those claims are allowed to do.

05 — Identity & Security

Seven techniques to protect your APIs

APIs are doors into your system. They need multiple layers of protection.

01

Rate limiting

Limit requests per user, IP, endpoint, or system.

02

CORS

Controls which browser origins can call your API.

03

Injection defense

Use parameterized queries or safe ORM mechanisms.

04

Firewalls / WAF

Block suspicious traffic and known attack patterns.

05

VPNs for private APIs

Restrict internal APIs to trusted networks.

06

CSRF protection

Prevent malicious websites from abusing authenticated browser sessions.

07

XSS prevention

Escape and sanitize user-generated content before rendering it.

Security reminder: API security should be implemented in layers. Authentication alone does not make an API secure.
